# Agricultural Decision Engine v0.3 — proposed opt-in contract

`earthsync.engine.v0.3.0` is an implemented, additive Rust/JSON contract for
**checking supplied evidence**, not a released crop recommendation service.
Catalog and environmental owners must review this boundary before adopting it.
No Flutter, Python, NASA POWER, bridge, v0.2 or existing integration interface is
changed. No new dependencies, services, model runtime or internet are required.

## Entrypoints and examples

```rust,ignore
v03::analyze_v03(&Request) -> Result<ResultV03, ValidationError>
v03::analyze_v03_json(&str) -> String
field_shift_engine::analyze_v03_json(&str) -> String // same function
```

The JSON function always returns a versioned success/error envelope. The typed
entrypoint validates before computing. Malformed JSON, unknown fields/enum
variants, dangling sources, invalid dates/units, nonfinite values and arithmetic
overflow return `input_or_source_validation_failure`; no partial success or
overflow-to-null result is returned. Error messages do not echo raw requests.

Runnable examples are in `engine/tests/fixtures/v03/`:

- `synthetic_request.json`: fictional crop identities and thresholds across four
  production systems. Four growing days spanning New Year exercise climate,
  soil, ETc and explicit fallow. Every rule and source is labeled synthetic.
- `unknown_request.json` / `unknown_response.json`: exact public JSON example
  with no sources, profile or environment; the result remains unknown.

From repository root:

```sh
cargo run --offline --locked --manifest-path engine/Cargo.toml --example v03_demo
cargo run --offline --locked --manifest-path engine/Cargo.toml --example v03_demo -- --stdin \
  < engine/tests/fixtures/v03/unknown_request.json
```

The full synthetic output is generated by the executable; it includes the whole
request as `context`, not just a successful arithmetic excerpt. The synthetic
record gives GDD = 60 °C days, growing-period rainfall = 10 mm, ETc = 12 mm and
two explicitly recorded fallow days. Those are software expectations, not crop
requirements or scientific validation results.

## Wire format

Canonical typed definitions: `engine/src/v03/types.rs`. All input structs reject
unknown fields; enums use snake_case. `?` below means nullable/absent `Option`.
All other fields, including arrays and booleans, are required. Empty arrays
explicitly supply no records; missing observations never become zero.

| Type | Fields |
| --- | --- |
| Request | `schema_version`, `day_basis`, `mode`, `region_id?`, `approximate_user_location?`, `farm?`, `photos[]`, `climate_intent`, `sources[]`, `catalog[]`, `observations[]`, `climate[]`, `history_complete`, `history[]`, `scenarios[]`, `sequential_field`, `candidate_window?` |
| Source | `id`, `title`, `citation`, `url?`, `published_on?`, `reviewed_on?`, `review`, `limitations[]` |
| Profile | `id`, `crop_id`, `family`, `cultivar?`, `system`, `approved_for_candidates`, `review`, `rules[]` |
| Rule | `id`, `review`, `source_ids[]`, `applicability`, `requirement`, `limitations[]` |
| Applicability | `regions[]`, `systems[]`, `cultivar?`, `field_only` |
| Plan | `id`, `crop_id`, `profile_id`, `system`, `cultivar?`, `period` |
| Scenario | `id`, `plans[]` (declared sequence order) |
| CandidateWindow | `period`, `system` |
| Observation | `id`, `property`, `value?`, `unit`, `depth?`, `provenance` |
| DailySeries | `id`, `day_basis`, `variable`, `unit`, `provenance`, `days[]` |
| DailyValue | `date`, `value?`, `quality` |
| Provenance | `kind`, `source_ids[]`, `period?`, `retrieved_on?`, `issued_on?`, `spatial`, `quality`, `uncertainty?`, `method?` |
| Cycle | `id`, `crop_id?`, `profile_id?`, `fallow`, `period?`, `provenance` |
| ConfirmedFarm | `field_id`, `point?`, `boundary?`, `confirmed_on` |
| Photo | `id`, `captured_on?`, `location?`, `source_ids[]` |
| Point | `latitude`, `longitude` (finite WGS84 degrees) |
| Date / Period | `{year, month, day}` Gregorian years 1–9999 / `{start, end}` inclusive |
| Depth | `top_cm`, `bottom_cm` (finite, nonnegative top, strictly larger bottom) |
| Bounds | `min`, `max` inclusive finite ordered bounds |

`mode`: `evidence_assessment` or `software_test`. `climate_intent`:
`historical` or `forecast`. Review states: `reviewed`, `unreviewed`,
`reference_only`, `synthetic`. Reviewed sources need a review date. Per-profile,
per-rule and source review are separate assertions; all must pass. In real
assessments synthetic provenance cannot supply a positive or negative criterion.
Software mode permits synthetic arithmetic and labels every finding
`software_test_only`; whole scenarios remain insufficient.

Crop IDs include explicit versions (`test.crop@1`). Profiles identify individual
production systems: `dryland`, `rainfed`, `irrigated`, `flooded_lowland`. Profile
crop, production system and cultivar must match the selected plan. Unknown crop
or absent profile produces unknown; an incompatible profile is not applicable.
Rule IDs are globally unique; `catalog.*` and `schedule.*` identify reserved
engine contract checks. Profiles for one versioned crop must agree on family.
No crop alias matching, cultivar substitution or
unreviewed threshold fallback is performed.

Empty rule `regions` explicitly means global applicability. Otherwise an exact
request region must match; scope also requires a listed production system and
any specified cultivar. Region IDs and context review must come from catalog and
adapter owners; coordinate labels never establish scope. Myanmar, Iowa and all
other locations are equally valid inputs.

## Evidence and spatial support

`kind`: `observed`, `modeled`, `forecast`, `farmer_reported`, `synthetic`,
`unavailable`. `quality`: `usable`, `missing`, `suspect`, `unavailable`. Missing
and unavailable values must be null; suspect values are retained but not used.
Known supplied values validate even when another criterion/day is missing.

`SpatialSupport` is explicitly tagged:

```json
{"scope":"field","field_id":"farmer-confirmed-field-id"}
{"scope":"regional","region_id":"reviewed-region-id","resolution_m":250}
{"scope":"unknown"}
```

Field evidence requires a matching confirmed farm ID. Regional evidence requires
a matching region and a rule permitting regional support (`field_only=false`).
There is no resolution threshold that converts a model/map cell into a field
measurement. Unknown support is unusable. Optional scale and uncertainty remain
explicitly unknown when absent, never invented. The adapter must review the
spatial association; the engine does not perform polygon/cell intersection.

The approximate user point, confirmed farm point/boundary and photo location are
separate. A boundary is an unclosed ring of at least three distinct vertices;
no area or topology is inferred. Photo metadata is retained and never converted
into soil, crop identity, climate or health evidence. An approximate user point
does not populate the farm or resolve a field ID.

`period` means the observation's declared **effective support**, not merely its
retrieval date. Undated evidence remains unknown. Soil/management observations
must explicitly cover the entire requested growing period; the engine does not
invent validity of an old soil sample or irrigation report into a future season.
Historical retrieval cannot precede effective-period end. Forecasts require an
issue date no later than valid-period start, and retrieval cannot precede issue.
The library has no current clock and makes no forecast freshness/safety claim.

All analysis dates use request `day_basis`, a nonblank owner-agreed daily calendar
convention. Every daily series must declare the same convention to be used. UTC,
NASA local solar time and farm civil dates are not silently mixed or converted.

## Implemented requirements

`requirement` is a tagged object with `condition` and the following fields:

| condition | Additional fields and semantics |
| --- | --- |
| `temperature` | `range_c: Bounds`; all daily Tmin/Tmax extremes must fit; this must not encode a source's seasonal-mean or stage-only temperature requirement |
| `growing_degree_days` | `base_c`, `range_c_days: Bounds`; uncapped daily mean GDD, supplied crop-specific base and bounds required |
| `growing_period_rainfall` | `range_mm: Bounds`; sum only the inclusive dated crop period, never annual rainfall |
| `duration` | `range_days: Bounds`; positive whole inclusive calendar-day duration, planting through harvest |
| `planting_window` | `first_mmdd`, `last_mmdd`; inclusive dates such as 1201–0131 wrap through New Year |
| `soil_numeric` | `property`, `range: Bounds`, `unit`, `depth: Depth`, `method?`; exact depth and any required method must match |
| `soil_category` | `property` (`texture` or `drainage`), `allowed[]`; exact owner-defined category IDs |
| `irrigation_required` | boolean availability check; not quantity, quality or adequacy |
| `flooded_management` | `required` category ID; exclusively for flooded-lowland systems, separate from drainage and irrigation availability |
| `crop_evapotranspiration` | `stages[]: {id, first_day, last_day, kc}`; supplied one-based inclusive stage offsets and coefficients; no interpolation or default Kc |
| `succession` | `previous_crop_id?`, `previous_family?`, `minimum_fallow_days`; at least one predecessor selector; both must match if both supplied |

Daily variables are `tmin`, `tmax` (unit `celsius`), `rainfall`, `et0`
(unit `mm_per_day`, interpreted as each declared day's integrated daily rate).
Records can be unordered; dates must be valid and unique, and inside any declared
series period. For each variable there must be exactly one overlapping selected
series; ambiguity is unknown, not automatic preference for a favorable model.
Historical intent accepts observed/modeled context; forecast intent accepts only
forecast data. Neither is relabeled. Every crop day must have a usable value;
incomplete periods report usable/expected/missing counts without extrapolation.
Tmin/Tmax pairs must be ordered, including supplied pairs alongside missing days.

GDD uses `sum(max(0, Tmin/2 + Tmax/2 - base_c))`. Dividing first avoids premature
mean overflow; accumulation and all computed quantities must stay finite. No
default 10 °C base, upper cap, maturity prediction or yield relationship is added.
The caller must supply evidence appropriate to this exact uncapped formula.

Supported numeric soil properties/units:

| property | Accepted units / exact conversions |
| --- | --- |
| `ph` | `ph`, finite; no universal chemical 0–14 or crop limit is assumed |
| `organic_carbon` | `g_per_kg` ↔ `percent_mass` (divide/multiply by 10); physical 0–1000 g/kg |
| `bulk_density` | `kg_per_m3` ↔ `g_per_cm3` (divide/multiply by 1000); positive |
| `soil_moisture` | `volumetric_fraction` ↔ `volumetric_percent` (multiply/divide by 100); physical fraction 0–1 |

Values are tagged `{ "type":"number", "value":6.5 }`,
`{ "type":"category", "value":"owner-defined-id" }` or
`{ "type":"boolean", "value":true }`. Texture, drainage and flood management
use `category` units; irrigation availability uses `boolean`. Unknown units or
invalid property/value combinations fail validation. Broad map classes are not
translated to laboratory properties, crop identities or farmer drainage.
Modeled wetness indices are not volumetric moisture inputs.

Original units, depth, model uncertainty, method, scale and source remain in
`context` and observation findings. No averaging/fusion chooses between farmer
and model evidence. Applicable usable records that disagree on a requirement
produce an unknown contradiction finding. Records at another depth, method or
validity period are not silently selected to resolve a contradiction.

ETc applies **FAO-56 chapter 5, equation 56**, `ETc = Kc × ET0`, for aligned daily
reference ET0 with a documented method and reviewed stage coefficients. Daily
results retain stage ID, coefficient, ET0, ETc, offsets and period; total ETc is
unknown if any ET0 day or Kc stage is missing. This implements standard-condition
single-coefficient arithmetic only: no stress correction, Penman–Monteith ET0
estimator, effective-rainfall calculation or soil-water balance. Rainfall and
monthly NASA T2M cannot fill missing ET0 or prove actual soil moisture.

FAO paddy guidance treats land preparation, percolation/seepage and the water
layer separately from ETc. This engine therefore has a separate reviewed flooded
management category check and does not invent those terms, universal standing
water depths or a paddy irrigation prescription.

## Rotation and generated candidates

Sequence order is caller-declared; it is never sorted into a favorable rotation.
With `sequential_field=true` and a confirmed farm, next planting must be strictly
after previous harvest. These are source-independent calendar checks, not crop
benefit claims. They run even when crop identity/profile is unknown. Attributed
field-history intervals (including explicit fallow) also detect plan overlaps.

Succession rules compare the preceding plan, or the chronologically latest
preceding non-fallow history cycle. History selection requires `history_complete`
and dated, usable attributed entries; overlapping crop history leaves selection
unknown. Crop family comes only from the matching catalog profile, not farmer
text or a crop-name heuristic. History profile/crop mismatches are errors.

The calendar gap is `next planting - preceding harvest - 1`. A positive fallow
requirement needs an explicit attributed fallow interval covering that gap;
missing history cannot establish fallow. Contradictory crop records within that
gap leave the fallow finding unknown. A zero-gap sequence can meet a sourced
zero-fallow requirement. No nitrogen credit, disease reduction, soil improvement
or yield benefit is inferred from legumes or repeated/different families.

Optional `candidate_window` produces one successor scenario per explicitly
approved catalog profile for that system with applicable reviewed rules and
sources. It uses the caller's dates, checks the same environment/history rules,
preserves catalog order, and does not rank, optimize or promise feasibility.
Generated IDs use reserved `candidate:` scenario prefix. Multi-crop alternatives
are supplied as ordinary scenarios and assessed using the same sequence logic.

## Results for Flutter and technical inspection

`{"status":"success","data":{schema_version, software_test_only, summaries,
findings, candidates, context, limitations}}` or
`{"status":"error","schema_version":"earthsync.engine.v0.3.0",
"error":{status,path,message}}`.

Each technical finding includes `scenario_id`, `plan_id`, `rule_id`, `condition`,
`status`, `input`, `requirement`, `units`, `source_ids`, `input_ids`,
`explanation`, `unknowns`, `limitations`, `software_test_only`. Source IDs resolve
to citations/review/limits in context; input IDs resolve to the original dated,
spatially supported record or identified plan. Engine catalog/calendar checks
identify the contract rule instead of fabricating an agronomic source.

| Finding status | Meaning |
| --- | --- |
| `supported_by_supplied_evidence` | This explicit comparison/calculation is supported within supplied scope; not whole-crop suitability |
| `conflicts_with_supplied_evidence` | A reviewed applicable requirement or declared calendar constraint conflicts |
| `insufficient_information` | Missing, ambiguous, contradictory, unusable or unreviewed evidence |
| `evidence_not_applicable` | Known crop/system/cultivar, regional/spatial, calendar-convention or historical/forecast mismatch |
| `input_or_source_validation_failure` | Input/source integrity failed; no scientific assessment emitted |

`summaries[]` preserves scenario order and includes a status, compact
`{plan_id, rule_id, status, message}` entries and unknowns for Flutter. Detailed
inputs/requirements stay in `findings`; full technical context stays separate.
No LLM is required. A real scenario can report a conflict; otherwise its whole
status remains insufficient because the supplied rule set is not demonstrably
exhaustive. Software-mode whole scenarios always remain insufficient. Supported
unrelated criteria never cancel a conflict. No weighted score, confidence
percentage, recommendation ranking or safe-forecast flag exists.

Inspected integration base `e0cdaaf875efb376e3081a66826b4b5e21601c67`, environmental

| Owner / existing data | Proposed boundary / required agreement |
| --- | --- |
| Crop catalog | Map stable versioned IDs, family, cultivar, system, per-rule review, sources, scope, exact statistics and limitations to `Profile`/`Rule`; supply reviewed real records. Do not reuse a mean-temperature source for daily-extreme bounds, annual rainfall for a crop season, or generic duration for an unsupported cultivar. |
| POWER/Python | Existing backend requests only T2M/PRECTOTCORR and returns complete-month summaries. Keep its API unchanged. New daily adapter must supply Tmin/Tmax, calendar convention, fill/quality states, exact dates, parameter lineage, grid support and ET0 method when actually available. Monthly means cannot reconstruct them. |
| Environmental source pack | Retain its research/reference status. No live adapter is installed by this branch. Undated SoilGrids estimates, incomplete provenance and modeled wetness remain unavailable for affected v0.3 comparisons, not promoted to reviewed field measurements. |
| Flutter/FRB | Keep existing passthrough and decoder. Opt into a new wrapper only after reviewing this schema; preserve all five statuses, synthetic labels, nulls and input order. User GPS, confirmed farm and photo metadata must be distinct inputs. |

No real crop requirements are bundled or implicitly approved by this engine
branch. Synthetic examples are deliberately isolated test records. External
catalog and new daily/soil/ET0 adapters remain **unavailable pending supplied,
reviewed records and schema agreement**. This is not an agricultural validation,
browser, Android or live NASA test claim. The existing v0.2/API behavior remains
available while those integrations are developed separately.
